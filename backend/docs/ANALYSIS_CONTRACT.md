## ตัวชี้วัดเชิงธุรกิจ

กำไรขั้นต้น = รายได้ − ต้นทุนขาย · กำไรจากการดำเนินงาน หักค่าใช้จ่ายดำเนินงานเพิ่ม ·
กำไรสุทธิ หักดอกเบี้ยจ่ายและภาษีเพิ่ม · ต้นทุนรวมนับค่าใช้จ่ายทั้ง 4 ประเภท

ต้นทุนต่อหน่วย = (ต้นทุนขาย + ค่าใช้จ่ายดำเนินงาน) / จำนวนหน่วยที่ขาย
**ไม่รวมดอกเบี้ยและภาษี**

กำไรส่วนเกินต่อหน่วย = ราคาขาย − ต้นทุนผันแปรต่อหน่วย · จุดคุ้มทุนปัดเศษ
ต้นทุนคงที่ / กำไรส่วนเกิน ขึ้นเป็นจำนวนหน่วยเต็มถัดไป · ถ้ากำไรส่วนเกินไม่เป็นบวก
จะ**ไม่มีจุดคุ้มทุนที่เป็นค่าจำกัด**

ROI แบบง่าย = กำไรสุทธิจากการลงทุน / เงินลงทุนเริ่มต้น × 100 สำหรับงวดที่ส่งมา
**ไม่แปลงเป็นอัตราต่อปี และไม่ได้หมายถึงการคำนวณ NPV หรือ IRR**

อัตราส่วนหนี้ = หนี้สิน / สินทรัพย์ · จำนวนเดือนของเงินสำรองใช้เงินสดไหลออกจากการดำเนินงาน
ที่ปรับเป็นฐาน 30 วัน **ไม่ใช่ค่าใช้จ่ายดำเนินงานตามเกณฑ์คงค้างหรือการชำระเงินต้น**

## Analysis API

`POST /api/analyze` และ alias `/api/v1/analyze` รับ:

```json
{
  "input": {"currency": "THB", "kind": "actual", "period_start": "2026-09-01", "period_end": "2026-09-30", "assets": "100000", "liabilities": "60000", "equity": "40000"},
  "use_llm": false
}
```

คำขอขั้นต่ำนี้ถูกต้องตามรูปแบบแต่ข้อมูลไม่ครบ จะได้ HTTP 200 พร้อม `insufficient_data`
ตัวชี้วัดเป็น null และเกรดเป็น null · งบที่ไม่สมดุลหรือ net income ที่ส่งมาไม่สอดคล้องกัน
จะได้ HTTP 422 · `use_llm` เป็น boolean แบบเข้มงวด

`POST /api/analyze/excel?use_llm=false` รับ workbook มาตรฐานผ่าน multipart field `file` ·
JSON และ Excel ใช้การตรวจสอบและการวิเคราะห์ชุดเดียวกัน · จำกัดขนาด 5 MiB และ
**ไม่เคยบันทึกไบต์ของ workbook ลงที่ใด**

`GET /api/analysis/example` คืนเฉพาะตัวอย่างสังเคราะห์ชุดคงที่ ติดป้าย `simulated` ·
`GET /api/analysis/template.xlsx` สร้าง workbook ที่นำเข้าได้ในหน่วยความจำ ·
ทั้งสองมี alias `/api/v1/` ด้วย

คำตอบของการวิเคราะห์มี metadata แบบ Envelope เดิม พร้อม `inputHash` และ
`schemaVersion: analysis-v1` · `data` มี `input` ที่ปรับรูปแล้ว, `metrics` เป็นสตริงทศนิยม,
`grading`, `indicators` ที่เข้ากับ UI, `findings` ที่จัดหมวดแล้ว, `explanation`,
`aiMode` และ `aiWarning`

**ทุก finding ต้องอ้างตัวชี้วัดที่มีอยู่จริงอย่างน้อยหนึ่งตัวผ่าน `evidenceIds`** ·
`dataUsed` ใน explanation มีค่าที่ใช้แสดงและ `targetElementId` ที่ตรงกับการ์ดในหน้า health ·
การตัดสินเกณฑ์ของ DSCR, สภาพคล่อง และจำนวนเดือนเงินสำรอง **ใช้ค่าที่ยังไม่ปัดเศษ**
ค่าที่แสดงจะปัดเฉพาะตอนนำไปแสดงผล

เส้นทางเหล่านี้เป็น stateless · ข้อมูลของผู้เรียกถูกส่งกลับให้ผู้เรียกเท่านั้น
และไม่ถูกใช้เป็น "ธุรกิจล่าสุด" ร่วมกับ client รายอื่น · ลายนิ้วมือ SHA-256 ใช้ระบุ input
ที่ปรับรูปแล้ว **ไม่ใช่การทำ anonymization ไม่ใช่การยืนยันตัวตน และไม่ใช่กลไกควบคุมสิทธิ์** ·
เบราว์เซอร์เก็บผลล่าสุดไว้ในหน่วยความจำและทำเครื่องหมายว่า stale เมื่อ input เปลี่ยน
ผลลัพธ์ไม่ถูกเก็บข้ามการรีโหลดหน้า

## โหมด rules และโหมดโมเดล (optional)

Rules ระบุ: การชำระหนี้ไม่พอ, กระแสเงินสดติดลบ, เงินทุนหมุนเวียนที่ยังไม่มีแหล่งทุน,
เงินสำรองไม่เพียงพอ, ส่วนของเจ้าของติดลบ, ขาดทุนในงวด และกำไรต่อหน่วยไม่เป็นบวก ·
จุดแข็งและจุดอ่อนก็ถูกบันทึกเมื่อมีหลักฐานรองรับ

**Rules ไม่อนุมานเรื่องลูกค้าจ่ายช้า ความผิดปกติของรายการ แนวโน้มอุตสาหกรรม
หรือเงินสดในอนาคต จากข้อมูลที่ไม่มี** · ส่วน unknowns ระบุชัดว่าการพยากรณ์แบบระบุวันที่
30-90 วัน และการวิเคราะห์ประวัติค่าใช้จ่าย อยู่นอกขอบเขตของ milestone นี้

> **หมายเหตุ (อัปเดต 2026-10-15):** ข้อความข้างต้นล้าสมัยแล้ว — `app/forecasting.py`
> ทำการพยากรณ์ 30/60/90 วันได้แล้ว และเปิดใช้ผ่าน `GET /api/forecast`

เกณฑ์ good/warning เป็นนโยบายเดโมที่ประกาศไว้ · การ์ดเรื่องต้นทุน PMT และจุดคุ้มทุน
เป็นข้อมูลประกอบ **ไม่ใช่การจัดอันดับแบบอุตสาหกรรม**

ค่าเริ่มต้น `aiMode: rules` ไม่ต้องใช้ credential ของโมเดล · หากต้องการให้โมเดลช่วย
จัดลำดับความสำคัญ ให้ตั้ง `OPENAI_API_KEY` และ `OPENAI_MODEL` **ที่ฝั่ง backend เท่านั้น**
แล้วส่ง `use_llm: true` · เลือกโมเดลที่รองรับ Structured Outputs ของ Responses API ·
**ไม่มีการสลับผู้ให้บริการหรือโมเดลแบบเงียบ ๆ** · **ห้ามใส่ความลับในตัวแปรที่ขึ้นต้นด้วย VITE**

โมเดลได้รับตัวชี้วัดที่คำนวณแล้ว เกรด และ finding ที่มีหลักฐานรองรับ
**ไม่ได้รับ workbook หรือข้อมูลติดต่อ** · คำขอตั้ง `store: false` ·
Structured Outputs บังคับให้คำตอบอ้างได้แค่ finding ID ที่มีอยู่
และ backend ปฏิเสธ ID ที่ไม่รู้จักและฟิลด์ที่เกินมา

**โมเดลเปลี่ยนตัวชี้วัด เกรด หลักฐาน หรือข้อความข้อเสนอแนะไม่ได้** ·
ทำได้แค่จัดลำดับ finding ภายในระดับความรุนแรงที่กำหนดไว้ และ
**ย้ายจุดแข็งความรุนแรงต่ำขึ้นไปเหนือความเสี่ยงระดับวิกฤตไม่ได้** · ไม่มี finding ใดถูกตัดออก

กรณี timeout ปฏิเสธ ตอบไม่ครบ หรือตอบผิดรูปแบบ จะถอยกลับไปใช้ rules
พร้อมแสดง `aiWarning` ให้เห็น · ข้อความ error ไม่เปิดเผย response body ของผู้ให้บริการ
หรือ credential · การเรียกโมเดลจริงต้องมี credential ที่ตั้งไว้ ส่วน unit test
ทดสอบขอบเขตของผู้ให้บริการด้วยคำตอบจำลอง

อ้างอิง: [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)

  `aiMode: openai`, `aiModel: gpt-6-luna`, `aiWarning: null`
- `max_output_tokens` ยังคงเป็น **600** และ `store` ยังคงเป็น **false** · ไม่ได้เพิ่ม
  การลองใหม่อัตโนมัติหรือสลับโมเดล · key อยู่เฉพาะใน `backend/.env` ที่ Git ละเว้น ·
  ไฟล์ตัวอย่างการตั้งค่าสภาพแวดล้อมมีเพียง model ID
- ตัวชี้วัดและเกรดของ `use_llm: false` และ `true` ตรงกันทุกไบต์เมื่อจัดรูปแบบ
  เป็น canonical JSON · finding ทุกฟิลด์ตรงกันเมื่อเทียบตาม ID เดิม ทั้งข้อความ action
  หลักฐาน และ severity · กรณีตัวอย่างคงลำดับอาร์เรย์เดิม ส่วนกรณีเงินสดขาดมือ
  สลับลำดับภายในกลุ่ม severity เดียวกัน จึงมี **ลำดับอาร์เรย์ต่างกัน** ·
  เมื่อขอให้โมเดลจัดลำดับ ระบบจึงไม่ได้รับประกันว่าอาร์เรย์ทั้งชุดจะตรงกันทุกไบต์
- เทสต์จำลองระดับ HTTP transport ครอบคลุม JSON ที่ถูกต้อง, HTTP/model JSON
  ที่ผิดรูปแบบ, การปฏิเสธ, timeout, 401/403, 429 และ 500 · กรณีล้มเหลวยังคง
  ผลจากระบบกฎเกณฑ์ พร้อม `aiWarning` ที่ไม่ว่าง โดยไม่เปิดเผยเนื้อหาคำตอบจาก
  ผู้ให้บริการหรือข้อมูลลับ · ชุดเทสต์อัตโนมัติไม่ได้เรียกโมเดลจริง
- ข้อความ `finding.text` และ `finding.action.text` ทั้ง 12 เงื่อนไขที่สร้างจาก
  ระบบกฎเกณฑ์เป็นภาษาไทยแล้ว เช่นเดียวกับ `explanation.summary` และ
  `explanation.reasoning` · key, ID, category, severity, หน้าปลายทาง และสูตรคงเดิม ·
  ชื่อตัวชี้วัด ข้อความอธิบายข้อมูลที่ยังไม่ทราบ และคำเตือนผู้ให้บริการเดิมยังใช้
  ภาษาอังกฤษเชิงเทคนิค · เส้นทางระบบกฎเกณฑ์คงตัวเลขทั้งหมด โดยเปลี่ยนเฉพาะภาษา
  ของคำอธิบายที่แสดงต่อผู้ใช้ตามที่ตั้งใจ
- ตรวจผ่าน HTTP จริงที่ `/api/v1/overview?sme_id=...` แล้ว ยืนยันว่า `title`,
  `description` และ `actionText` ของ SME เดโมทั้งสองรายเป็นภาษาไทย โดย ID `act-*` คงเดิม

## ข้อมูลเสริมสำหรับวิเคราะห์: forecast และประวัติค่าใช้จ่าย

```python
def build_analysis(
    data: FinancialInput,
    *,
    forecast: dict | None = None,
    expense_history: list[dict] | None = None,
) -> dict:
    ...
```

พารามิเตอร์ใหม่เป็น keyword-only และมีค่าเริ่มต้น `None` · Caller เดิมไม่ต้องแก้
และยังแจ้ง unknowns ตามเดิมเมื่อไม่ได้รับข้อมูลเสริม · Core ไม่เรียกฐานข้อมูล
หรือคำนวณ forecast ซ้ำ · ตัวชี้วัดทางการเงินเดิมทั้ง 18 รายการ เกรด และ `inputHash`
ยังคำนวณจาก `FinancialInput` เดิมเท่านั้น · เวลา `analyzedAt` ยังคงสร้างแยกแต่ละคำขอ

เมื่อส่งข้อมูลเสริม จะเพิ่ม `data.contextEvidence` ซึ่งเป็น dict ที่ค้นด้วย evidence ID ·
`finding.evidenceIds` ใหม่อ้างถึง dict นี้และ `explanation.dataUsed` · หลักฐานเดิมยังอ้าง
ตัวชี้วัดเดิม · เพิ่มแถวใน `indicators` โดยใช้โครงสร้างแถวเดิมสำหรับค่าตัวเลขที่มีหลักฐาน
เพื่อให้ `targetElementId` มีเป้าหมายจริง · หลักฐานวันเริ่มขาดเงินสดเชื่อมไปยังตัวชี้วัด
เงินสดต่ำสุด · ไม่มีการเปลี่ยนชื่อหรือลบ key, finding ID, category หรือ severity เดิม

### หลักเกณฑ์การรับ forecast

- ส่งผลจาก `forecast_cashflow()` โดยตรง · หากใช้คำตอบจาก `GET /api/forecast`
  ให้ส่งเฉพาะ `response["data"]` ไม่ใช่ envelope ทั้งชุด
- รับเฉพาะ THB และสถานะ `ok` หรือ `insufficient_data` · เงินที่อ้างต้องเป็นจำนวน
  ที่มีค่าจำกัด และวันที่ต้องอยู่ในช่วงที่รองรับ
- อ้างยอด 30/60/90 วันเฉพาะค่าที่ไม่เป็น null และมี `schedule_complete_through`
  ครอบคลุมวันปลายงวดนั้น · ไม่ใช้ค่า `conditional_*` เป็นข้อสรุปที่ยืนยันแล้ว
- อ้างเงินสดต่ำสุดและวันเริ่มขาดเงินสดเฉพาะ forecast สถานะ `ok` ที่ยืนยันครบ 90 วัน ·
  หากยังไม่ครบ ให้แจ้ง unknowns และไม่สร้าง finding สองชนิดนี้
- การขาดเงินสดใช้เกณฑ์เดียวกับ forecaster: ต่ำกว่าเงินสำรองที่ระบุ หรือยอดติดลบ
  เมื่อไม่ได้ระบุเงินสำรอง · เก็บวันที่และเกณฑ์ในหลักฐาน และใช้ข้อความไทยระบุว่าเป็นค่าคาดการณ์
- Finding ID ใหม่คือ `forecast_cash_shortfall`, `forecast_minimum_cash` และ
  `forecast_horizon_balances` · หลักฐานได้แก่ `forecast_first_shortfall_date`,
  `forecast_minimum_cash` และ `forecast_balance_30_days` / `forecast_balance_60_days` /
  `forecast_balance_90_days`

### นโยบายเปรียบเทียบค่าใช้จ่าย `expense-history/v1`

- `expense_history=None` หมายถึงยังไม่ทราบ · `[]` หมายถึงสอบถามแล้วไม่พบรายการ
  และจะคืน `data.expenseComparison.status="known_empty"` โดยไม่สร้างคำเตือนผิดปกติ
- รับแถวตาม loader: `id`, `date`, `category`, `amount` · ฟิลด์อื่นรับได้แต่ไม่ถูกส่ง
  ต่อเป็นหลักฐาน · จำนวนเงินต้องไม่ติดลบ · รวมรายการ ID เดียวกันที่เหมือนกันหนึ่งครั้ง
  และปฏิเสธ ID ซ้ำที่วัน หมวด หรือจำนวนเงินขัดแย้งกัน
- Caller ต้องส่งข้อมูล SME เดียวกัน · หากมี `sme_id` ในแถวและพบหลาย SME จะปฏิเสธ ·
  loader ของ Claude ปัจจุบันกรอง SME ให้แล้ว แต่ไม่ได้ส่ง `sme_id` ในทุกแถว
- เดือนที่เปรียบเทียบคือเดือนของ **รายการล่าสุดในประวัติที่ส่งมา** · ไม่ใช้วันที่เครื่อง
  และไม่บังคับให้ตรงงวดบัญชี · เช่น งบล่าสุดเดือนกันยายนยังรับประวัติค่าใช้จ่ายตุลาคมได้
  โดยหลักฐานระบุเดือนและวันข้อมูลล่าสุดแยกชัดเจน
- เทียบหมวดเดียวกันกับยอดรวมรายเดือนของตัวเองในสามเดือนปฏิทินก่อนหน้า ·
  ต้องมีข้อมูลอย่างน้อยสองเดือนและผลรวมฐานมากกว่า 0 · เดือนที่ไม่มีรายการเป็น unknown
  ไม่ใช่ 0 และบันทึกใน `missing_months` พร้อม unknowns
- ฐานคือผลรวมของเดือนที่มีข้อมูลหารจำนวนเดือนที่มีข้อมูล · แจ้งเตือนเมื่อยอดเดือนที่
  เปรียบเทียบ **สูงกว่าฐานเกิน 50%** · ค่าที่เพิ่มเท่ากับ 50% พอดีไม่ถูกแจ้งเตือน ·
  ตัดสินด้วยสมการต่อไปนี้ก่อนปัดเศษ:

```text
current_total * observed_month_count > baseline_sum * 1.50
```

- `data.expenseComparison` เก็บเวอร์ชันนโยบาย ช่วงเปรียบเทียบ เดือนที่มี/ขาดข้อมูล
  ยอดรวมแต่ละเดือน ค่าเฉลี่ย เปอร์เซ็นต์เพิ่ม และ `source_ids` เพื่อคำนวณซ้ำได้ ·
  finding ใช้ ID `unusual_expense_<category_sha256_prefix>` และอ้างหลักฐาน
  `expense_current_<category_sha256_prefix>` กับ `expense_baseline_<category_sha256_prefix>`
- คัดกรองเฉพาะรายการที่ส่งมา · เดือนล่าสุดอาจยังไม่จบ และ loader อาจจำกัดจำนวนแถว
  จึงไม่ได้รับรองว่าประวัติครบ ไม่สรุปว่าผิดปกติเมื่อไม่มีฐาน และไม่กล่าวหาว่าทุจริต

  กรกฎาคม–กันยายน 99,166.67 ได้ **+69.41%** และเกิด finding · หมวดสาธารณูปโภค
